## 2. AI Layer / intent classification

There are exactly **two** LLM call sites in this codebase, both under `ai/`, and the codebase is explicit about that being an invariant (repo-root `CLAUDE.md` principle 2):

1. `ai/intent_classifier.py::classify_intent` / `classify_intent_with` — single-shot NL → structured tool call.
2. `ai/llm_client.py::narrate_risk_figure` / `complete` (used inside `ai/chat.py`'s tool-calling loop) — narration of already-computed numbers.

### Is it rule-based or an LLM call?

**Purely an LLM call — no keyword/regex-based intent matching exists anywhere.** The classifier forces a tool call via `tool_choice={"type": "any"}` so the model cannot answer in free text:

```python
# ai/intent_classifier.py
_ROUTER_TOOL_NAME = "route_request"

_CLASSIFIER_SYSTEM_PROMPT = (
    "You route a user's question to exactly one Cypher tool. You do not "
    "answer the question, do not describe what the answer might be, and do "
    "not produce any number — you only choose the tool and fill in its "
    "arguments. ..."
)


def classify_intent_with(
    transport: LLMTransport, user_message: str, available_tools: list[str]
) -> ToolCall:
    ...
    message = transport.create_message(
        system=_CLASSIFIER_SYSTEM_PROMPT,
        messages=[{"role": "user", "content": prompt}],
        tools=[_router_tool(available_tools)],
        tool_choice={"type": "any"},  # forced tool choice: must route, never answer
    )
```

`ai/chat.py`'s `ChatEngine` is a hand-written tool-calling loop (deliberately *not* using an SDK's agentic "tool runner" helper — see its module docstring) that lets the model pick from the full tool catalogue across up to `DEFAULT_MAX_TOOL_ITERATIONS = 6` round trips, then narrates.

### Defined intents/categories

There is no separate "intent" enum. The set of things the model can be routed to *is* the tool registry — see §3. `ai/intent_classifier.py`'s `available_tools` argument must be a subset of `ai.tool_registry.tool_names()`; anything else raises `ValueError`.

### Where the LLM is invoked — model/provider, call site, prompt template

- **Provider:** Groq (`ai/groq_transport.py`), OpenAI-shaped chat-completions API.
- **Default model:** `DEFAULT_GROQ_MODEL = "openai/gpt-oss-120b"` (overridable via `GROQ_MODEL` env var; must support tool calling).
- **Max output tokens:** `DEFAULT_GROQ_MAX_TOKENS = 8_192`.
- **Client construction:** lazy, in `ai/llm_client.py::get_transport()` — `GroqTransport()` is only instantiated on first use, so a missing API key surfaces as `LLMConfigurationError` at call time, not import time.
- **Call sites:**
  - `ai/intent_classifier.py::classify_intent_with` → `transport.create_message(...)` with a forced-tool-choice router.
  - `ai/chat.py::ChatEngine.run_turn` / `stream_turn` → `transport.create_message` / `transport.stream_message`, looped with the full tool catalogue.
  - `ai/llm_client.py::narrate_risk_figure` → single non-streaming call, prompt = "narrate this JSON verbatim, invent nothing."
- **System prompts (verbatim, abridged):**
  - Classifier (see above).
  - Chat (`ai/chat.py::CHAT_SYSTEM_PROMPT`): "You are Cypher, the assistant for this platform... Every figure you report must come from a tool call in this conversation. You never compute, estimate, approximate... A verifier checks every number in your reply against the actual tool results..."
  - Narration (`ai/llm_client.py::NARRATION_SYSTEM_PROMPT`): "You narrate cyber-risk figures that have already been computed by a deterministic Open FAIR + Monte Carlo engine. You never compute, estimate or adjust a figure yourself..."
- **Translation boundary:** `ai/groq_transport.py` is the *only* place that knows Groq's OpenAI-shaped message format (`message.tool_calls`, `role: "tool"`). Everything else in `ai/` speaks a provider-neutral content-block shape (`text` / `tool_use` / `tool_result` blocks, modeled on Anthropic's Messages API shape). `to_groq_messages`, `to_groq_tools`, `from_groq_message` are pure dict-in/dict-out functions, unit-tested without any network call.

### References to "Jev", "TypeSafe AI", or "System One"

**None found.** A case-insensitive grep across `*.py`, `*.ts`, `*.tsx`, `*.md`, `*.json`, `*.yaml` for `jev|typesafe|system one|system-one` turned up nothing except an unrelated base64 fragment inside a `package-lock.json` integrity hash (`...zt6OdqaDoOnJ1ZYsCYGt9YmWzDXl4vQdKTyJev62gFhRGKdx7mcT54V9KIjg...`) — a coincidental substring match, not a reference to anything. ### Registry / dispatch mechanics (`ai/tool_registry.py`)

- `ToolSpec` (frozen dataclass): `name`, `description`, `input_schema` (JSON Schema), `handler` (the callable), `unavailable_hint` (shown to the model when the handler raises `NotImplementedError`).
- `execute_tool(tool_name, arguments) -> ToolExecution`: validates args against the schema (drops unknown keys, checks required), calls the handler, and classifies the outcome into `status: "ok" | "unavailable" | "error"`. `NotImplementedError` → `"unavailable"` (never a fake empty/zero result); any other exception → `"error"`.
- `ToolExecution.to_model_content()` renders the result as the literal `tool_result` JSON the model sees — for a non-`"ok"` status it explicitly carries `"retry": false` and an `"instruction"` field telling the model to relay the gap, not fill it in:

```python
payload = {
    "status": self.status,
    "detail": self.detail,
    "retry": False,
    "instruction": (
        "Tell the user plainly that this figure has not been computed "
        "and why. Do not estimate, approximate or substitute a number."
    ),
}
```

### Numeric verification / guard step — **yes, exists and is fully implemented**: `ai/numeric_guard.py`

This is the enforcement point for "every number in LLM output must be traceable to a real computation." Pipeline:

1. `extract_numeric_claims(text) -> list[NumericClaim]` — regex-based extraction of every number-like substring in the LLM's prose, handling ₹/Rs./INR markers and Indian magnitude words (lakh/crore) as well as Western ones (million/billion), via `_CLAIM_PATTERN` and `_SCALE_WORDS`.
2. `collect_ground_truth(payload, prefix) -> dict[str, float]` — recursively flattens **every** numeric leaf of a real tool/engine result (including numbers embedded inside strings, e.g. a version like `"v1.2"`) into a dotted-path-keyed dict. Called on every `ToolExecution.result` in `ai/tool_registry.py::execute_tool`, and accumulated per-conversation in `ai/sessions.py::ChatSession.ground_truth`.
3. `verify_against_ground_truth(claims, ground_truth_values, tolerance) -> GuardResult` — each claim must match some ground-truth value within `DEFAULT_TOLERANCE = 0.01` (1%) relative difference (percent-suffixed claims are also tried as a fraction, e.g. "12%" vs `0.12`).
4. `guard_narration(text, ground_truth, tolerance) -> GuardResult` — the full pipeline; any unmatched claim is replaced in-place with `[UNVERIFIED: {claim}]` in `corrected_text`, which is what callers must display — never the raw model text.

```python
DEFAULT_TOLERANCE = 0.01  # ai/numeric_guard.py

_FLAG_TEMPLATE = "[UNVERIFIED: {claim}]"
```

`ai/chat.py::ChatEngine._finalize` calls `guard_narration` unconditionally on every assembled reply before constructing the `ChatReply`; there is no code path in `interfaces/` that can bypass it (`interfaces/api/app.py`'s chat routes only ever serialize an already-guarded `ChatReply`).

## 4. Engine / core

### FAIR engine — `core/engine/` (split by pipeline stage; **fully implemented**, unlike the rest of `core/`)

- `core/engine/models.py` — result types:
  ```python
  @dataclass(frozen=True)
  class LossEventContribution:
      scenario_id: str
      asset_id: str
      expected_annual_loss_inr: float
      description: str


  @dataclass(frozen=True)
  class RiskFigure:
      snapshot_id: str
      expected_annual_loss_inr: float
      value_at_risk_inr: float
      value_at_risk_percentile: float
      top_contributors: list[LossEventContribution]
      monte_carlo_iterations: int
  ```
- `core/engine/scenarios.py::build_loss_event_scenarios(snapshot)` — one scenario per (asset, unremediated finding) pair. Scenario id = `f"{asset_id}::{finding_id}"`. Remediated findings (`remediated_at` set) produce no scenario.
- `core/engine/parameterization.py::parameterize_scenario(scenario, snapshot)` — attaches Open FAIR parameters:
  - `_exposure_profile`: `"internet_facing_critical_asset"` if `network.internet_facing` and a related service is critical/high, else `"internal_asset"` — keys into `core.assumptions.BASELINE_THREAT_EVENT_FREQUENCY_PER_YEAR`.
  - `_exploit_probability`: finding's own `epss_score`, or `BASELINE_EXPLOIT_PROBABILITY_FOR_UNSCORED_FINDING` (0.05), floored to `KEV_LISTED_MINIMUM_EXPLOIT_PROBABILITY` (0.5) if `kev_listed`.
  - `_active_control_resistances`: only `mfa_enforced` and `edr_active` are currently observable from the schema.
  - `_combine_resistances`: `1 - Π(1 - resistance)` (never summed).
  - Loss magnitude: `BASE_LOSS_MAGNITUDE_BY_CRITICALITY_INR[worst_criticality_tier]` scaled by `RTO_MULTIPLIER_BY_BACKUP_POSTURE[worst_backup_posture]`.
- `core/engine/simulation.py::run_monte_carlo(parameterized_scenarios, iterations=None, seed=None)` — **the Monte Carlo simulation**:
  - Deterministic seed derived by SHA-256 hashing the scenario content (`_derive_deterministic_seed`) so "same snapshot ⇒ same figure" without threading a seed through every caller.
  - Each scenario's per-iteration rate is sampled from a Beta-PERT distribution (`_sample_pert`); loss event *count* that year is `Poisson(rate)`; each event's magnitude is its own Beta-PERT draw; the year's scenario total is their sum (compound structure → heavy tail, not `frequency × magnitude` point multiplication).
  - **Shared latent control-health factors** (`_sample_shared_control_health`): one draw per control category per iteration, shared across every scenario relying on that control — this is the engine's resolution of "scenario independence" (SIH105 Notion doc Conflict Register item C3): a bad iteration for a shared control (e.g. EDR fleet-wide failure) raises loss across every dependent scenario simultaneously, inducing real positive correlation instead of naive independent summation.
  - Returns `{"iterations", "seed", "total_annual_loss_samples_inr", "per_scenario_annual_loss_samples_inr"}`.
- `core/engine/risk_figure.py::compute_risk_figure(snapshot) -> RiskFigure` — orchestrates scenarios → parameterize → `run_monte_carlo`, then `expected_annual_loss_inr = mean(total_samples)`, `value_at_risk_inr = percentile(total_samples, VALUE_AT_RISK_PERCENTILE*100)`, `top_contributors` sorted descending by per-scenario mean.

`core/assumptions.py` (362 lines) is the single home for every modelling constant, each documented with **ASSUMPTION / JUSTIFICATION / CALIBRATION** comment blocks; every value is explicitly flagged as a PLACEHOLDER pending real calibration (e.g. `CONTROL_RESISTANCE_STRENGTH = {"mfa_enforced": 0.4, "edr_active": 0.5}`, `MONTE_CARLO_ITERATIONS = 10_000`, `VALUE_AT_RISK_PERCENTILE = 0.95`, `PERT_CONFIDENCE_FACTOR = 4.0`).

### Optimizer — `core/optimizer.py` (**implemented** — see the 2026-09-26 update at the top of this document)

### What the "gate" is supposed to check (design, from docstrings — not yet executable)

1. **`check_asset_count_delta`** — reject if the candidate's asset population changed implausibly vs. the previous snapshot (signals a partial connector failure, not real churn).
2. **`check_no_findings_from_unreachable_scanners`** — reject any finding whose `provenance.connector` is listed in the candidate's own `scan_scope.unreachable_scanners` (internally inconsistent data).
3. **`check_criticality_present_or_unknown`** — reject any finding with `criticality: null` (never evaluated = defect); the literal string `"unknown"` is a legitimate, distinct outcome and must pass.
4. **`check_provenance_non_null`** — reject any finding with missing/null/empty `provenance.connector` or `provenance.raw_source_id`.
5. **`check_no_ordinal_in_numeric_field`** — reject a candidate where a schema-numeric field (e.g. `epss_score`, `rto_hours`) contains a string ordinal like `"High"`.

`validate_snapshot` must run all 5 without short-circuiting and return every `GateResult`; `commit_snapshot` must never be called on a candidate that failed any gate (fail-safe: previous snapshot stays current).

Note: `interfaces/cli/cypher.py::ingest_command` already calls `validate_snapshot`/`commit_snapshot` and handles the fail path correctly (`typer.echo` per failed gate, then returns without committing) — it is written against the intended contract even though the functions it calls are stubs today.

## 9. Gaps — designed but not (yet) built in code

Cross-referencing repo-root `CLAUDE.md`'s principles/design against actual code:

1. **[Corrected 2026-09-26] `core/optimizer.py` is implemented**, not a stub — see the update note at the top of this document. `core/snapshot.py`'s status (all 5 gates, `validate_snapshot`, `commit_snapshot`) is unverified since 2026-09-22; a live snapshot store was observed under `data/snapshots/` during the 2026-09-26 work, which contradicts this bullet's premise for `core/snapshot.py` too, but that subsystem was not itself re-audited.
2. **No snapshot store/persistence exists.** `SNAPSHOT_STORE_PATH` is defined in `.env.example` but nothing reads/writes it; `commit_snapshot` (which would persist) is itself a stub. `interfaces/cli/cypher.py::ingest_command` hardcodes `previous = None` with an explicit `# TODO: read the actual current snapshot once a snapshot store exists`.
3. **All 6 `ai/tools/` wrappers are stubs** (`raise NotImplementedError`), because what they'd call (`core.engine`'s scoped entry points, `core.snapshot`, `core.optimizer`, `governance.mapper`) is partially or fully unimplemented. This means the chat assistant and `/exposure`, `/optimize` API routes currently answer every question with a structured "unavailable" result, never a number — which is the intended fail-safe behavior of `ai.tool_registry.execute_tool`, working as designed even though nothing is implemented yet.
4. **5 of 9 connectors are unimplemented stubs**: `cmdb_connector.py` (the intended canonical asset-identity source), `iam_connector.py`, `nessus_connector.py`, `nmap_connector.py`, `threat_intel_connector.py`. Only Wazuh, Greenbone, Prowler, ScoutSuite are implemented and wired into `cypher ingest`.
5. **Asset identity resolution is a placeholder.** With no real CMDB connector, every implemented connector mints its own `host:`/`cloud:`-prefixed id from a private `_identity_hint` bridging key (documented explicitly in `infra/README.md` as temporary).
6. **`schema/aggregated_assets.schema.json` has several open `TODO`s in field descriptions** that are explicitly "known open design questions, not implementation gaps" (per `schema/README.md`): `services[].criticality`'s allowed value enum is not yet fixed; `scan_scope.coverage`'s per-asset granularity is undecided; `assets[].edr.detection_rules_active`/`recent_alerts` shape is undefined; the endpoint↔asset relationship is unresolved.
7. **`core/assumptions.py`'s `COST_PER_RECORD_INR` and `EXPECTED_REGULATORY_PENALTY_INR` are populated but not wired into `core.engine`** — the schema has no records-affected-count or regulatory-regime field to key them by yet (explicitly noted in both the constants' own comments and `parameterize_scenario`'s "Known gap" docstring section). Loss magnitude today is criticality-tier-driven only, not decomposed into FAIR's full primary/secondary loss forms.
8. **`core/assumptions.py`'s `CONTROL_RESISTANCE_STRENGTH` only has 2 of 4 intended categories populated** (`mfa_enforced`, `edr_active`); `patch_current` and `network_segmentation` are commented out pending a connector that exposes the relevant per-asset signal.
9. **CLI stub commands**: `validate-snapshot`, `run-engine`, `optimize`, `framework-status` all raise `NotImplementedError` (only `ingest` is real), because they depend on the unimplemented `core/` functions above.
10. **API/dashboard route mismatch**: the dashboard client (`interfaces/dashboard/src/lib/api.ts`) calls `/frameworks/{framework}/status`, `/snapshot`, and `/snapshot/gates`, but **none of these three routes exist in `interfaces/api/app.py`** — only `/exposure`, `/optimize`, `/health`, and the `/chat*` family are registered. This is a real gap between two pieces of already-written code, not just a documented TODO.
11. **`docker-compose.yml` is an explicit skeleton** ("Nothing here is wired up... Do not deploy this as-is") — no built images, no real secret management.
12. **Multi-worker/production session storage does not exist.** `ai/sessions.py::InMemorySessionStore` is explicitly process-local and not shared across API workers; a shared store would need to be built behind its interface for a multi-worker deployment.
13. **No numeric ML/scoring model exists anywhere** (by design — principle 1). There is no "AI Layer" beyond the two LLM call sites described in §2; no intent taxonomy separate from the tool registry; no keyword-based classification path at all (contrary to what one might expect from "AI Layer" terminology — it's 100% LLM tool-routing, no rules engine).
14. **No references to "Jev", "TypeSafe AI", "System One", or any "Local LLM" concept exist in this codebase** — the only model integration is the hosted Groq API (§2, §8). If this terminology comes from an external spec or notion doc, it has not yet been reflected into code here.
